This document describes how each Lean 4 definition in `formal-verification/lean/FVSquad/`
corresponds to the original C++ source. It records the correspondence level, known
divergences, and the impact on proved theorems.

**Correspondence levels**:

| Level | Meaning |
|-------|---------|
| **exact** | Lean function computes identical results to the C++ on all modelled inputs |
| **abstraction** | Lean models a pure subset; correctness properties hold within the abstraction |
| **approximation** | Lean diverges from C++ in a known, documented way |
| **mismatch** | Lean definition is incorrect relative to the C++ in a way that may invalidate proofs |

**Divergences**:
- **Type**: Lean uses `Int`; C++ is templated (`float`, `double`, `int32_t`, etc.)

characterise the *logical structure* of the clamping operation for ordered types without
NaN. Float NaN behaviour is explicitly out of scope and documented.

### `PX4.Math.signNoZero`

| Lean name | C++ name | C++ location | Correspondence | Notes |
|-----------|----------|--------------|---------------|-------|
| `PX4.Math.signNoZero` | `math::signNoZero<T>` | [`src/lib/mathlib/math/Functions.hpp#L52`](../src/lib/mathlib/math/Functions.hpp#L52) | **abstraction** | Integer model; C++ uses bool subtraction |

**Divergences**:
- **Type**: C++ returns `int` from `bool` subtraction; Lean returns `Int`.
- **C++ expression**: `(T(0) <= val) - (val < T(0))` computes as `1 - 0 = 1` or
  `0 - 1 = -1`. The Lean model `if 0 ≤ val then 1 else -1` captures the same logic.
- **Float NaN**: `0 ≤ NaN` is false and `NaN < 0` is false in IEEE 754, so
  `signNoZero(NaN) = 0 - 0 = 0`. **This is a known divergence**: the Lean model returns
  1 for all non-negative inputs including NaN (which is not modelled), while the C++ would
  return 0 for NaN. Since the safety theorem `signNoZero_ne_zero` is a key property
  (ensures no division-by-zero in callers), maintainers should be aware that the C++
  version CAN return 0 for NaN float inputs.

**Impact on proofs**: Run 101 adds 5 new theorems: `signNoZero_mul_self_nonneg`
(the product `signNoZero(x) * x ≥ 0`, i.e., multiplication by the sign yields a
non-negative magnitude), `signNoZero_neg_of_pos` (`signNoZero(-x) = -1` when `x > 0`),
`signNoZero_pos` (`signNoZero(x) = 1` when `x > 0`), and two concrete instances
`signNoZero_one`, `signNoZero_neg_one`. The total is now 11 theorems for `signNoZero`.
The NaN divergence is a genuine concern for float callers — the safety property
`signNoZero_ne_zero` does NOT hold for C++ float inputs when `val` is NaN.

**Recommendation**: Callers that use `signNoZero<float>` and divide by the result should
ensure NaN cannot reach `signNoZero`, or the C++ should be patched to assert/clamp NaN.

### `PX4.Math.countSetBits`

| Lean name | C++ name | C++ location | Correspondence | Notes |
|-----------|----------|--------------|---------------|-------|
| `PX4.Math.countSetBits` | `math::countSetBits<T>` | [`src/lib/mathlib/math/Functions.hpp#L276`](../src/lib/mathlib/math/Functions.hpp#L276) | **abstraction** | Nat model; C++ uses while loop with bit shift |

**C++ source**:
```cpp
template<typename T>
int countSetBits(T n) {
    int count = 0;
    while (n) { count += n & 1; n >>= 1; }
    return count;
}
```

**Lean definition**: Structural recursion on `Nat` — `countSetBits 0 = 0`,
`countSetBits (n+1) = (n+1) % 2 + countSetBits ((n+1) / 2)`.

**Divergences**:
- **Type**: C++ template; Lean uses `Nat`. The C++ template is typically instantiated
  with `uint32_t` or `uint64_t`. For these types the semantics match exactly.
- **Signed types**: If the C++ template is instantiated with a signed type and `n < 0`,
  the right shift `n >>= 1` is implementation-defined in C++. The Lean model only
  applies to `Nat` (non-negative values).
- **Loop vs recursion**: The C++ while loop is equivalent to the structural recursion for
  non-negative inputs (the loop terminates and extracts the same bits).

**Impact on proofs**: The 9 concrete `native_decide` examples and the inductive
`countSetBits_pow2` theorem are valid for `Nat`. Run 101 adds 6 further theorems:
`countSetBits_zero`, `countSetBits_one`, `countSetBits_double` (doubling preserves bit
count), `countSetBits_succ_odd` (odd step adds 1), the key safety theorem
`countSetBits_pos` (any positive `n` has at least one bit set, proved by well-founded
recursion), and `countSetBits_eq_zero_iff_zero` (zero-count iff zero-input).
The correspondence to C++ `uint32_t` and `uint64_t` is exact for non-negative values.

### `PX4.AlphaFilter.alphaUpdate`

| Lean name | C++ name | C++ location | Correspondence | Notes |
|-----------|----------|--------------|---------------|-------|
| `PX4.AlphaFilter.alphaUpdate` | `AlphaFilter<T>::updateCalculation` | [`src/lib/mathlib/math/filter/AlphaFilter.hpp#L79`](../src/lib/mathlib/math/filter/AlphaFilter.hpp#L79) | **abstraction** | Rational model; float NaN/overflow not modelled |

**C++ source**:
```cpp
template <typename T>
T AlphaFilter<T>::updateCalculation(const T &sample) {
  return _filter_state + _alpha * (sample - _filter_state);
}
```

**Lean definition**:
```lean
def alphaUpdate (state alpha sample : Rat) : Rat :=
  state + alpha * (sample - state)
```

**Divergences**:

1. **Explicit arguments**: C++ reads `_filter_state` and `_alpha` from class fields; the
   Lean model takes them as explicit `Rat` arguments. The correspondence is exact when
   `state = _filter_state` and `alpha = _alpha` at the time of the call.

2. **Type**: C++ is templated (`float`, `double`, `Vector3f`, etc.). The Lean model
   uses `Rat` (arbitrary-precision rationals). IEEE 754 NaN, infinity, and rounding are
   not modelled.

3. **Quaternion specialisation**: `AlphaFilter<Quatf>` uses a specialised axis-angle
   interpolation rather than the scalar formula. Only the scalar/Euclidean case is modelled.

4. **`setParameters` / `setCutoffFreq`**: The relationship between the cut-off frequency
   and `_alpha` (`alpha = 1 - exp(-2π·f_c·dt)`) is not modelled; `alpha` is taken as a
   direct input assumed to lie in `[0, 1]`.

5. **State mutation**: C++ mutates `_filter_state` in place (`_filter_state = result`).
   The Lean model is pure: callers compose `alphaUpdate` calls explicitly.

**Impact on proofs**: All 12 proved theorems hold for the rational model. The key
safety properties (no-overshoot in both directions, monotonicity in sample and state,
and the closed-form exponential convergence formula) are valid for the abstract model.
For float callers, the NaN/rounding divergence limits applicability to well-formed,
bounded inputs — as expected in flight-control contexts.

### `PX4.SlewRate.slewUpdate`

| Lean name | C++ name | C++ location | Correspondence | Notes |
|-----------|----------|--------------|---------------|-------|
| `PX4.SlewRate.slewUpdate` | `SlewRate<Type>::update` | [`src/lib/slew_rate/SlewRate.hpp#L79`](../src/lib/slew_rate/SlewRate.hpp#L79) | **abstraction** | Pure functional model; state, float, and dt not modelled |

**C++ source** (relevant lines 79–87):
```cpp
Type update(const Type new_value, const float deltatime)
{
    const Type dvalue_desired = new_value - _value;
    const Type dvalue_max = _slew_rate * deltatime;
    const Type dvalue = math::constrain(dvalue_desired, -dvalue_max, dvalue_max);
    _value += dvalue;
    return _value;
}
```

**Lean model**:
```lean
def slewUpdate (current target max_step : Int) : Int :=
  let d := target - current
  current + if d < -max_step then -max_step
            else if d > max_step then max_step
            else d
```

**Divergences**:

1. **Mutable state elided**: The C++ `update` method mutates `_value`. The Lean model
   takes `current` (= `_value` before the call) as an explicit argument and returns the
   new value. The correspondence is: `slewUpdate(current, target, max_step)` = value of
   `_value` after `update(target, dt)` where `max_step = _slew_rate * dt`.

2. **Float arithmetic**: C++ uses `float`/`double` for `Type` and `deltatime`. The Lean
   model uses `Int`. This abstracts away IEEE 754 rounding, NaN, and infinity. In
   practice the slew rate operates on actuator setpoints that are bounded floats, so NaN
   is not expected, but the proof does not cover it.

3. **`_slew_rate * deltatime` product**: The Lean model takes `max_step` as a single

## Known Mismatches

**`negate<int16_t>` involution failure** (severity: low–medium):

The Lean 4 proof `negate16_not_involution` formally establishes that
`math::negate<int16_t>` is **not** a global involution:

```
negate(negate(-32767)) = negate(INT16_MAX) = INT16_MIN = -32768 ≠ -32767
```

Counterexample (bit pattern 32769 = -32767):
- `negate(32769)` = 32767 (= INT16_MAX), via the standard `return -value` branch
- `negate(32767)` = 32768 (= INT16_MIN), via the `if (value == INT16_MAX)` special case
- `negate(negate(32769))` = 32768 ≠ 32769

**Root cause**: The `INT16_MAX → INT16_MIN` special case is incorrect. In standard two's
complement, `-INT16_MAX = -32767` is representable in `int16_t` without overflow, so the
special case is unnecessary and causes round-trip failure for any value whose negation
equals INT16_MAX (i.e., for `value = -32767`).

**The only value needing a special case** is `INT16_MIN = -32768`, since
`-INT16_MIN = +32768` overflows `int16_t`.

**Correct fix**:
```cpp
template<>
constexpr int16_t negate<int16_t>(int16_t value)
{
    if (value == INT16_MIN) {
        return INT16_MAX;  // -(-32768) would overflow; saturate to INT16_MAX
    }
    return -value;
}
```

**Involution holds for**: all `int16_t` values except `value = -32767` under the
current (buggy) implementation. With the fix, it would hold universally.

**Risk in practice**: IMU drivers (`ICM42670P.cpp:608-634`, `BMI085_Accelerometer.cpp:504-505`)
use `math::negate` to flip sensor axes. A value of exactly -32767 (= 0x8001) in the
raw sensor data would be incorrectly round-tripped if negation is applied twice. This
is unlikely in practice (raw IMU data must hit exactly -32767) but represents a
correctness defect.

**Related theorem**: `negate16_not_involution`, `negate16_counterexample` in
`formal-verification/lean/FVSquad/Negate.lean`.

---

**`signNoZero` and NaN** (severity: medium):

The C++ `math::signNoZero<float>` returns **0** for NaN inputs (both comparisons
`T(0) <= val` and `val < T(0)` are false for NaN, so the expression evaluates to
`0 - 0 = 0`). The Lean model does not model NaN and the `signNoZero_ne_zero` theorem
does not hold for C++ float NaN inputs.

**Affected theorem**: `signNoZero_ne_zero`

**Risk**: Any caller that uses `signNoZero<float>` result as a divisor or sign multiplier
without first checking for NaN could divide by zero if NaN propagates to the argument.
A search of `signNoZero` callers in the codebase is recommended.

**Recommended fix**: Add a `static_assert(!std::is_floating_point_v<T>)` to the C++
template (forcing callers to use integer types or to clamp NaN before calling), or
change the implementation to `return std::isfinite(val) ? ((T(0) <= val) ? 1 : -1) : 1`.

## `Crc16Fold.lean` — CRC-16 Fold Property

**C++ source**: `src/drivers/gnss/septentrio/util.cpp`
**Function**: `septentrio::buffer_crc16(const uint8_t* data_p, uint32_t length)`

### What is modelled

The per-byte CRC-16 update step (`crc16Step : UInt16 → UInt8 → UInt16`) mirrors the
C++ loop body exactly. The buffer CRC function (`crc16`) is defined as
`List.foldl crc16Step 0`, which directly models the `while (length--)` loop.

The C++ pointer `data_p` and counter `length` are abstracted as a `List UInt8`.

### Correspondence level: **Exact**

Lean's `UInt8` and `UInt16` types carry the same modular arithmetic (mod 2⁸ and
mod 2¹⁶) as C's `uint8_t` and `uint16_t`. The bitwise operations (`^^^` for XOR,
`>>>` for unsigned right shift, `<<<` for left shift, `.toUInt8` / `.toUInt16` for
width conversion) match their C counterparts exactly for all inputs.  No abstraction
penalty: the Lean model and the C++ function agree on every possible input.

### Divergences

| Aspect | C++ behaviour | Lean model | Impact |
|--------|--------------|-----------|--------|
| Memory access | Pointer + length counter | `List UInt8` | Same semantics; no UB |

### What is modelled

`crc16_add` processes one byte through the CRC-16-CCITT shift register (polynomial

```c
    const uint64_t poly = 0x42F0E1EBA9EA3693ull;
```

### Overview

`PID.lean` models PX4's generic PID controller (`PID::update`, `PID::updateIntegral`,
`PID::updateDerivative`). The three C++ methods are translated into pure Lean functions
operating over `Int`, enabling fully automated `omega`-based proofs without Mathlib.
The `PIDState` structure carries the integral accumulator and `Option Int` for the last
feedback value (`none` = first call, encoding the C++ `NaN` initial condition).

### C++ Source Reference

```cpp
// src/lib/pid/PID.cpp:38–57
float PID::update(const float feedback, const float dt, const bool update_integral) {
    const float error = _setpoint - feedback;
    const float output = (_gain_proportional * error) + _integral
                       + (_gain_derivative * updateDerivative(feedback, dt));
    if (update_integral) updateIntegral(error, dt);
    _last_feedback = feedback;
    return math::constrain(output, -_limit_output, _limit_output);
}
void PID::updateIntegral(float error, const float dt) {
    const float integral_new = _integral + _gain_integral * error * dt;
    if (std::isfinite(integral_new))
        _integral = math::constrain(integral_new, -_limit_integral, _limit_integral);
}
float PID::updateDerivative(float feedback, const float dt) {
    float feedback_change = 0.f;
    if ((dt > FLT_EPSILON) && std::isfinite(_last_feedback))
        feedback_change = (feedback - _last_feedback) / dt;
    return feedback_change;
}
```

### Divergences

1. **`Int` vs `float`**: The model operates over `Int` rather than `float`. This
   abstracts away IEEE 754 NaN/±∞/rounding. The key safety properties (output clamping,
   anti-windup, equilibrium, monotonicity) all transfer to floating-point when NaN is
   excluded.

2. **`update_integral` flag**: The C++ `update_integral` parameter controls whether
   the integral is updated on each call. The Lean model always updates the integral
   (always `true`). This means `pidNextState` and `pidOutput` correspond to the
   `update_integral=true` execution path only.

3. **`std::isfinite(integral_new)` guard**: The C++ only updates the integral if
   the new value is finite (to prevent wind-up from NaN/∞). In the `Int` model,
   arithmetic never produces NaN/∞, so this guard is vacuously satisfied.

4. **`FLT_EPSILON` threshold on `dt`**: The C++ uses `dt > FLT_EPSILON` to guard
   the derivative computation. The Lean model uses `dt > 0`, which is equivalent
   for integers and a correct abstraction for the `Int` model.

5. **Mutable state**: The C++ uses mutable fields (`_integral`, `_last_feedback`).
   The Lean model replaces these with a pure functional `PIDState` record and explicit
   state-threading functions (`pidNextState`).

### C++ source summary

`WelfordMeanVector<Type, N>` implements Welford's online algorithm for simultaneously
updating the mean vector and the M2 matrix (un-normalised covariance) in one pass.
The C++ implementation:

1. On first call (`count == 0`): resets state, sets `count = 1`, initialises mean.
2. On overflow (`count == UINT16_MAX`): normalises M2 and resets count to 1.
3. Otherwise: increments count, updates mean (with optional Kahan summation), updates M2.

Key update formulas (ignoring Kahan):
```
count++
delta = x - mean
mean += delta / count
delta2 = x - mean  (new mean)
M2 += outer(delta, delta2)
```

### Divergences

- **Specialised to 2D**: the C++ template is parameterised by `N`; the Lean model handles only the `N = 2` case (2D vectors with scalar components `x` and `y`).
- **Kahan summation omitted**: the C++ mean update uses Kahan compensation (`_mean_accum`) to reduce floating-point accumulation error. The Lean model uses direct rational addition.
- **Integer arithmetic**: the model uses `Rat` throughout; the C++ type parameter `Type` is typically `float`.
- **Count overflow handling omitted**: the C++ resets and renormalises when `count == UINT16_MAX`. The Lean model does not model this edge case.
- **First-call reset omitted**: the C++ reset branch on `count == 0` is handled by the model's initial zero state; the model does not model the explicit `reset()` + `count = 1` path.

- ✅ Count increment on each step.
- ✅ Mean convergence: `mx` and `my` converge to the empirical mean of a list.
- ✅ M2 diagonal non-negativity: `m00 ≥ 0` and `m11 ≥ 0` are invariants of the update.
- ✅ M2 off-diagonal step formula: explicit recurrence for `m01`.
- ✅ **PSD invariant** (`welfordVec2_psd`): the 2×2 M2 matrix satisfies `m01² ≤ m00 * m11` after every step — the key covariance matrix semi-definiteness property.
- ✅ Multi-step (`FoldFrom` and `Fold` variants): count, mean invariants, M2 non-negativity, and PSD hold over arbitrary lists of observations from any initial state.
